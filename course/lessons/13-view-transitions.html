The View Transitions API

The View Transitions API is the closest the web has come to magic: tell the browser "the DOM is about to change," and it animates between the old and new states — even morphing one element into another across that change.

Normally, changing the DOM is instant and jarring. The View Transitions API changes that: wrap your DOM update in document.startViewTransition(...) and the browser snapshots the before and after, then crossfades between them. Give two elements the same view-transition-name and it does something remarkable — it morphs the first into the second, animating position, size and shape.

Grid → detail, morphed

Click a tile. Instead of snapping, it smoothly expands into the detail view — and collapses back when you close it. The thumbnail and the detail share a view-transition-name, so the browser knows they're "the same thing" and tweens between them. No animation library involved.

Live demo · click a tile
src/lib/ViewTransitions.svelte 
<script lang="ts">
  import { flushSync } from 'svelte';

  // The View Transitions API animates between two DOM states for you. You change
  // the DOM inside document.startViewTransition(...), and the browser crossfades —
  // or, for elements sharing a `view-transition-name`, *morphs* one into the other.
  type Shot = { id: number; title: string; hue: number };
  const shots: Shot[] = [
    { id: 1, title: 'Aurora', hue: 265 },
    { id: 2, title: 'Tide', hue: 180 },
    { id: 3, title: 'Ember', hue: 330 },
    { id: 4, title: 'Dusk', hue: 220 }
  ];

  let openId = $state<number | null>(null);

  function go(next: number | null): void {
    // Progressive enhancement: if the API is missing, just swap state.
    if (!document.startViewTransition) {
      openId = next;
      return;
    }
    document.startViewTransition(() => {
      openId = next;
      flushSync(); // force Svelte to apply the DOM change *inside* the transition
    });
  }
</script>

<div class="wrap">
  {#if openId === null}
    <div class="grid">
      {#each shots as shot (shot.id)}
        <button
          class="thumb"
          style="--h: {shot.hue}; view-transition-name: shot-{shot.id}"
          onclick={() => go(shot.id)}
        >
          {shot.title}
        </button>
      {/each}
    </div>
  {:else}
    {@const shot = shots.find((s) => s.id === openId)!}
    <button
      class="detail"
      style="--h: {shot.hue}; view-transition-name: shot-{shot.id}"
      onclick={() => go(null)}
    >
      <span>{shot.title}</span>
      <small>click to close</small>
    </button>
  {/if}
</div>

The Svelte detail that trips everyone up: flushSync. Svelte applies state changes asynchronously, but the View Transitions callback needs the DOM updated synchronously so it can snapshot the new state. Import flushSync from svelte and call it inside the callback right after you change state. Forget it and you'll get a crossfade of the old state into itself — no morph.

The killer feature: cross-page transitions in SvelteKit

View Transitions shine most between routes — a thumbnail on a list page that morphs into the hero image on the detail page, like a native app. SvelteKit makes this a few lines in your root layout using the onNavigate hook:

src/routes/+layout.svelte 
<script lang="ts">
  import { onNavigate } from '$app/navigation';

  let { children } = $props();

  // Drop this in your root +layout.svelte and EVERY client-side navigation in the
  // app becomes a view transition. Elements that share a `view-transition-name`
  // across the two pages will morph from one into the other.
  onNavigate((navigation) => {
    if (!document.startViewTransition) return;

    return new Promise((resolve) => {
      document.startViewTransition(async () => {
        resolve();
        await navigation.complete; // wait for the new page to be ready
      });
    });
  });
</script>

{@render children?.()}

Add a matching view-transition-name to the element on both pages and SvelteKit + the browser handle the morph across the navigation. This single hook, in your layout, upgrades your entire app's page changes to cinematic transitions.

Always feature-detect with if (!document.startViewTransition) return; and let the change happen instantly as a fallback — support is strong but not universal. And a unique view-transition-name must appear only once on screen at a time, or the browser can't decide what morphs into what.
