Nested & Reusable Timelines

Real productions aren't one long timeline — they're timelines inside timelines. Build small, reusable sequences and nest them into a master, and suddenly the most complex choreography becomes readable and maintainable.

A single flat timeline works for a hero, but it falls apart at scale — change one duration near the start and you're hand-tuning everything after it. The professional pattern is nesting: write a function that returns a small timeline for one piece, then master.add() those pieces into a parent. Each piece keeps its own internal timing; the master positions them.

Four cards, four mini-timelines, one master

Each card has its own little intro (slide → dot pop → bar wipe), built by a reusable cardIn() function. The master timeline slots all four in with an overlap. Replay it.

Live demo · nested timelines
src/lib/NestedTimeline.svelte 
<script lang="ts">
  import { gsap } from 'gsap';
  import type { Attachment } from 'svelte/attachments';

  const cards = ['Capture', 'Compose', 'Cut', 'Color'];

  // A reusable function that returns a self-contained timeline for ONE card.
  // Because timelines are objects, we can build small ones and slot them into a
  // bigger one — the key to keeping complex sequences readable and DRY.
  function cardIn(el: Element): gsap.core.Timeline {
    const q = gsap.utils.selector(el);
    return gsap
      .timeline()
      .from(el, { y: 40, opacity: 0, duration: 0.5, ease: 'expo.out' })
      .from(q('.dot'), { scale: 0, ease: 'back.out(2)', duration: 0.4 }, '-=0.2')
      .from(q('.bar'), { scaleX: 0, transformOrigin: 'left', duration: 0.5 }, '-=0.25');
  }

  const orchestrate: Attachment<HTMLElement> = (node) => {
    const ctx = gsap.context(() => {
      const master = gsap.timeline({ defaults: { ease: 'power2.out' } });
      // Slot each child timeline onto the master, overlapping by 0.35s. Change one
      // child and the master re-times itself automatically.
      node.querySelectorAll('.card').forEach((card, i) => {
        master.add(cardIn(card), i * 0.35);
      });
    }, node);
    return () => ctx.revert();
  };
</script>

<div class="deck" {@attach orchestrate}>
  {#each cards as card (card)}
    <div class="card">
      <span class="dot"></span>
      <strong>{card}</strong>
      <span class="bar"></span>
    </div>
  {/each}
</div>

Why nesting is a superpower

  • Reusability. cardIn() is written once and used for every card. Need a fifth card? It animates correctly for free.
  • Local control, global timing. Each child owns its internal choreography; the master only decides when each child starts. Separation of concerns, for animation.
  • Composability. A child timeline can itself contain children. You can build a whole page intro as a tree of timelines, then control the entire thing with one master.play(), .reverse() or .timeScale().
add() takes a position too. Just like tweens, master.add(childTimeline, position) accepts a time, a label, or a relative offset like '-=0.35' or '<'. So you compose at two levels: positions inside each child, and positions of the children within the master. That two-level control is exactly how title sequences and product tours stay perfectly in sync no matter how much you tweak them.

The capstone lessons lean on this hard: a cinematic intro is really a master timeline orchestrating a backdrop sub-timeline, a headline sub-timeline (with its own SplitText stagger), and a UI sub-timeline — each authored independently, then assembled.
