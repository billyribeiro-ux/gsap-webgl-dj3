Writing Three.js by hand means imperatively creating objects, adding them to the scene, wiring a render loop, handling resize and disposing everything on cleanup. Threlte wraps all of that in Svelte components. You declare your scene — <T.Mesh>, <T.PointLight> — and Threlte runs the renderer, the loop and the lifecycle for you. It's reactive too: change a prop with $state and the 3D updates instantly.

About this demo. Threlte is a Svelte library, so it needs a build step — it can't run in a plain HTML file like this page. The live demo below is the same scene rendered with vanilla Three.js so you can see the result; the code panels show the real Threlte version you'll paste into your SvelteKit app. They produce an identical spinning torus knot.

The mental model

  • <Canvas> — the one wrapper. It builds the renderer, default scene, camera fallback, render loop and resize handling. Everything 3D goes inside it.
  • <T.X> — any Three.js class becomes a component. <T.Mesh> is new THREE.Mesh(); its props are the object's properties; its children are its constructor args (geometry, material). If you know Three.js, you already know Threlte.
  • useTask — Threlte's render loop hook. The callback runs every frame with a delta. This replaces your manual requestAnimationFrame — and Threlte cleans it up automatically.

Why frame-rate independence matters

Notice mesh.rotation.y += delta * 0.6 instead of a fixed += 0.01. delta is the time since the last frame, so the knot spins at the same real-world speed whether the user is on a 60Hz laptop or a 144Hz gaming monitor. Hard-coding per-frame increments is one of the most common 3D bugs — multiply by delta and it disappears.

Setup in your SvelteKit app: pnpm add three @threlte/core @threlte/extras. The @threlte/extras package adds the goodies — orbit controls, GLTF model loading, environment maps, instancing — that turn a demo into a product. Next lesson: linking 3D to scroll and driving it with GSAP.
