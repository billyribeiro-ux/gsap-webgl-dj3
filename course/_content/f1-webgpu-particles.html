WebGL can render a lot, but it can't easily compute — there's no first-class way to run a general parallel program on the GPU. WebGPU changes that with compute shaders. Here, a million particles' positions live in a GPU storage buffer; each frame a compute pass updates every one of them in parallel, and a render pass draws them as additive points. The CPU's only job is to say "go." Move your cursor to pull the swarm.

The compute pipeline

  • State in a storage buffer. A single GPU buffer holds all million particles (position + velocity, 16 bytes each = 16 MB). It never leaves the GPU. The compute shader binds it as read_write; the render shader binds the same buffer as read.
  • Workgroups = parallelism. The compute entry point runs once per particle, in batches of 64 (@workgroup_size(64)). We dispatchWorkgroups(count / 64) and the GPU schedules thousands of threads. Each thread reads its particle, applies the flow field and cursor pull, and writes the result back — true data-parallel simulation.
  • Two passes, one buffer. Per frame we record a compute pass (simulate) then a render pass (draw count points) into one command encoder and submit. The render reads the freshly-updated buffer in its vertex shader — no copy, no round-trip to the CPU.
This is the GPGPU lesson, without the texture gymnastics. Remember ping-ponging positions through textures in WebGL? Compute shaders let you read and write a plain buffer directly — far cleaner, and it scales to millions. The same machinery runs boids, cloth, hair, particle physics, even neural-net inference. Compute shaders are why WebGPU isn't just "WebGL 2.0" — they unlock a category of work the browser simply couldn't do before.
