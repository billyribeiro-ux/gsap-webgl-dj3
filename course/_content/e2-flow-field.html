To move thousands of particles smoothly, you must get the CPU out of the loop. GPGPU (general-purpose GPU) is the trick: store each particle's position in a texture, then run a shader that reads every position, nudges it along a flow field, and writes the new position to a second texture — ping-pong, just like the simulation lesson. A point cloud then reads those positions in its vertex shader. The particles live entirely on the GPU.

The data-as-texture mindset

  • A texture is just a 2D array of vec4s. A 128×128 texture holds 16,384 RGBA values — perfect for 16,384 particle positions (xyz in RGB). Resize the texture and you have a million particles with no code change.
  • The sim shader integrates motion. It reads a position, evaluates a flow() function there (here a smooth swirling field — upgrade it to curl-of-noise for true turbulence), adds that velocity, and writes the result. Out-of- bounds particles respawn from a hash. This is numerical integration, per pixel.
  • The render reads positions back. The point cloud's vertex shader does texture2D(positions, particleRef).xyz to place each point. The geometry stores only a tiny "reference" coordinate per particle — the heavy data stays on the GPU.
Half-float for renderable state. Render targets that you both write and read each frame must use a renderable float type — HalfFloatType is the safe, widely-supported choice (full FloatType isn't guaranteed colour-renderable everywhere). It carries plenty of precision for positions. This same GPGPU scaffolding — a state texture, a sim shader, ping-pong targets, a render that reads the state — is the blueprint for boids, cloth, hair, and full fluid solvers. And WebGPU compute shaders are the next step: the same idea without the texture gymnastics, scaling to millions.
